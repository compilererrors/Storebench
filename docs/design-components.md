# Storebench design components

Every screen in Storebench is built from the shared components in `macos/Sources/StorebenchApp/DesignSystem` and the tokens in `macos/Sources/StorebenchCore/Resources/design.json`. Use them instead of raw SwiftUI controls, menus or tables, so buttons, rows and grids look and behave the same everywhere and people recognize where things are. These rules follow Apple's Human Interface Guidelines for [buttons](https://developer.apple.com/design/human-interface-guidelines/buttons), [layout](https://developer.apple.com/design/human-interface-guidelines/layout) and [settings](https://developer.apple.com/design/human-interface-guidelines/settings).

## Layout and density

Pages use 16–24 pt outer margins, 16 pt card padding and 12 pt between related components. Keep fields, their explanations and their commands together. Cards in a grid share a height within each row; longer copy wraps inside its column instead of widening the grid.

Settings use 8 pt between rows, one label column and a shared 300 pt control column. Narrow panes stack the control below its label. Field labels and hints each reserve one text line; static explanations grow when they need more room. A field whose feedback is shown separately can set its hint track to zero. Card headings group a small icon, a 15 pt title and its description on the same leading edge. A heading's accessory, such as an options menu, sits on the title's line without making that line taller, so cards with and without one line up. Empty text tracks do not reserve several explanatory lines.

A card taller than the page keeps its own top in view while you scroll through it, such as one language among many in Localizations or Text and Screenshots. The pinned top covers only that card's width, shows its title and description, and is pushed up by the card's end; nested cards read outer to inner. Cards that fit on the page never pin. Scrolling over the pinned top scrolls the page, and clicking it goes to the card's top.

What you are looking at stays where it is. When content above it changes height, such as a checklist row that is resolved, a status that is read again or a card that loads, the page moves by the same amount in the same layout pass, before the next frame is drawn. The page keeps the first card or row that starts in view; a card or row you are reading that grows opens downward. When something in view is removed, such as a resolved row or a removed language, nothing above it moves and what is below moves up into the gap, as in Mail or Finder. A page at its top stays at its top, and a field the app is placing in view keeps its own placement until you scroll. While you scroll, with a mouse wheel or a trackpad and its momentum, the page follows your scroll alone: content that changes meanwhile, such as rows shown as they come into view or statuses read again, never pulls it back. Dialogs keep one size set by the window, and their bodies scroll inside it, so their commands never move. Rows keep their commands in place while a check runs, dimmed with the reason, so no row changes height.

Back and Forward answer Command-[ and Command-], the mouse's side buttons and a swipe between pages, as in Safari and Finder, and their buttons name their shortcut on hover. They show a page where you left it from the first frame. The saved position is applied in the same pass that shows the page; if its content has not all arrived yet, the page holds that position with room below it until the content is there, so it never shows its top first and then jumps. Scrolling while the content arrives keeps your new position. Pages keep their last reads in memory for the window, so returning to one, such as the Overview's release cards, shows it at once and reads it again in the background.

Tables use 32 pt headers and 44 pt rows. Full cell values remain available through the shared value inspector. Metric cards keep a compact label, value and explanation with their neighbors aligned.

## Table tools

`StorebenchTableControls` uses a native macOS search field with immediate results, a compact Sort menu and a Rows per Page menu. A scoped Filter menu shows the selected filter in its accessible value and hover help. These tools keep the shared control-height track; narrow views wrap without widening their surrounding cards. `StorebenchDataTable` groups tools, column headings, rows and the result/page footer in one surface. Column headings can sort, dividers can resize, and row actions belong in a trailing menu. Alternating system row colors help track wide tables. The full-value inspector stays available on click, with its info affordance shown on hover rather than repeated prominently in every cell.

Sheets keep a compact title row, a scrolling body with 16 pt insets and a separate command footer. Related sections use the same 12 pt spacing as workspace pages.

## Selections and menus

Selection fields use macOS popup buttons, with the system's menu placement, checkmarks, focus ring and keyboard navigation. A long selected value keeps its full title and explanation in hover help and VoiceOver. Searchable selections use a bounded list with arrow-key navigation. Independent options use native checkboxes; exclusive radio choices use compact shared rows that grow with their labels and support arrow keys.

Command menus group related actions with native separators and submenus. Keep destructive actions separate from ordinary commands. Section navigation uses quiet links; it does not compete with Save or Connect actions.

## Commands and their context

Secondary commands belong to the content they control. Cards and sections accept a compact header accessory; collection records keep it beside their disclosure, outside the expand and collapse target. A closed record keeps its menu available. Use `StorebenchIconMenu` for several secondary commands and `StorebenchIconButton` for a single recognizable action such as Refresh. Both use the shared square control footprint, hover help and an accessible name that identifies their scope.

Field commands sit beside the input through `StorebenchFormField` or `StorebenchPicker`'s accessory. Model refresh stays beside the model, and account options beside the account. Keep Save, Add, Connect and reviewed Sync actions visible in the form's command area.

Collection sort, page size, order, default expansion and page-wide expand or collapse actions live in the list's View Options menu beside its result count. Language card menus control that language's text section visibility, remembered across versions. The All Languages submenu explicitly applies a layout everywhere. Opening or closing one language's text section never changes another language's height. Layout preferences never change listing text.

Disclosure actions preserve the clicked heading's existing position in every enclosing native viewport, for both opening and closing. They never scroll an already visible heading to the top or force keyboard focus away from an editor. This applies to workspace pages, settings, sheets, nested inspectors and bulk layout commands. A shrinking page keeps only the scroll range needed to avoid clamping the working position; ordinary scrolling releases it without moving the content. Later measurements preserve the heading until a newer interaction takes over. Explicit navigation and Edit requests still reveal their destination. Use immediate layout updates. Language text headings repeat the language and name the fields inside the section. Separators distinguish adjacent text sections and the language card's heading from its editor.

## Pricing model context

Prices by Country or Region starts with the shared Price Model option group and its native Price Strategy selector. Keep the chosen model's explanation, guide price and country preview together. Show CSV input only for manually entered prices. Alternative pricing editors stay out of the selected model's workspace; Apple prices are shown for Apple's strategy or an explicit comparison. Keep Countries with No or Few Purchases available beside the focused workflow. Choosing a model changes local presentation and never approves a price update.

Preview Prices becomes Cancel Calculation in the same command slot while running. Reserve one status track for the source or Apple price-matching progress. Show calculated model amounts while Apple matches are checked, and distinguish Checking, Not Checked, No Estimate and No Match. Only a completed preview with a matched guide price can be saved. Changing an input cancels the obsolete calculation; a late result cannot replace the current model or feedback.

## Media ordering

Use the shared material selection, drag source and card toolbar for screenshot and preview ordering. A click selects; Command-click toggles membership and Shift-click selects a range. A double-click opens the screenshot. The visible Actions menu and native context menu expose the same move commands, with destructive actions separated at the end.

Show selection with a border and checkmark. Show insertion with one narrow accent edge and a subtle glow in the destination gap, after the preceding visible card when one exists. Dragging several records preserves their original relative order. Hover changes only feedback; committing a drop updates the order once. Keep the source enabled during its native drag session, and animate only the committed card movement and insertion feedback, respecting Reduce Motion.

## Image inspection and crop tools

Image viewers keep Previous and Next together, zoom in its own group, and Download Original at the trailing edge. The shared media toolbar keeps these groups intact and uses two rows in narrow sheets. Zoom Out and Zoom In use adjacent minus and plus buttons; both stay visible at the zoom limits. A native slider and percentage popup share that row. The popup offers Fit Image and magnification presets; double-click switches between Fit and 100%.

Crop editors reuse the same zoom controls with a 100–400% range. Recenter Crop belongs beside Crop and Zoom, while orientation, frame settings and file quality stay with their own labels. Keep the last rendered preview visible until its replacement is ready, preserving its proportions. Card navigation, duplication and Undo/Redo use compact shared tools beside the card list; destructive commands stay in its options menu.

## Guide step bar

Every guide, such as Release, Quick Release, Set Up Pricing, Start Testing, Set Up Reports, Create Media and the no-sales pricing guide, keeps its Back and Next in one bar fixed to the bottom of the page. Its leading edge names the open step and what it still needs; its trailing edge has Back, then the step's own commands, then Next in the same place on every step, or the page the guide continues to on its last step. A step's own commands are those it finishes with, such as Save Draft, Add for Review or Save All to Asset Library; when one of them is the step's main command, Next is shown as secondary. Steps whose page holds several forms, such as the TestFlight pages in Start Testing, keep each form's Save Draft and Sync to Apple with that form, and the review it prepares is named in the bar. A command that cannot run now is dimmed and says why, including Back on the first step and Next before the guide has read what its steps need. The bar keeps one height, and the page leaves room for it, so the last field never sits under it. A review waiting to be sent is named in the same bar with Go to Review, so the page never shows two bars. A sync to Apple being sent is named there too, with how many of its steps are done and a progress bar in a fixed track, on every page of the window. When it ends the bar says Synced to Apple for a few seconds. A sync that stopped stays named with Go to Resolve, which opens the page that started it and shows why. A review still being prepared after Run in Background is named there too, as Preparing review; when it is ready the bar says Ready to send with Go to Review, and when none could be prepared it says Review not prepared with Go to Resolve. Commands in the bar never send anything by themselves; Add for Review still opens the guarded review. Option-Command-[ and Option-Command-] go to the previous and next step. In a dialog, which has no page bar, the same commands sit at the end of the step.

Create Media has five steps: Display Size and Cards, Screenshots, Text and Background, Save to Asset Library and Add in Text and Screenshots. Create Cards and Create AI Cards both open step 1, and cards made with AI open in step 2 to be checked. Step 2 shows only the card type and screenshot settings and step 3 only the text and background settings, beside the same preview. Save Draft sits in the bar on the first four steps and rests while every change is saved; step 4 adds Save All to Asset Library and step 5 Open Release Step 2, which saves changed cards first. None of them contacts Apple: Release uploads the cards only after its review is approved.

## Release submission

Every guide uses the shared step grid: a step list beside one working pane, stacked above it on narrow windows. Beside the pane the step list stays in view while the page scrolls: it moves with the page until it reaches the top edge, stays there and stops at the end of the step. A list taller than the window keeps its end in view instead. Release, Quick Release, pricing setup, Start Testing, Set Up Reports, Create Media and Lower Prices for countries with no or few purchases all show it; in Lower Prices, earlier steps can be opened again and a later step waits for the one before it.

Release and Quick Release open at once from the versions saved on this Mac. When a new version needs the current material from App Store Connect, it is read in the background while the page is open: the version number and release option can already be entered, and Save Draft or Sync to Apple pressed meanwhile is kept and carried out as soon as the material arrives, and once the material arrives the suggestion follows it, keeping what was typed. Background preparation starts the open app's material download before its other reads.

Quick Release always prepares a new version. It continues only a version Apple still lets you edit, such as one in Prepare for Submission; otherwise step 1 suggests the next number, copied from the newest version's listing and screenshots. When the version it was preparing has been submitted, Quick Release shows that version as done with Prepare Version and the next number, which starts the next version on this Mac without changing anything at Apple. Release keeps following a submitted version until it is out.

Quick Release uses this step grid with a fixed step rail beside one working pane. The numbers 1–4 stay visible beside status icons and labels. Its four steps are Prepare Release, What's New in This Version, Add Build and Add for Review. Back and Next move inside Quick Release. The version, What's New and build steps each end with Save Draft and Sync to Apple; Sync to Apple opens the review for creating the version, saving its text or adding the build. Until App Store Connect has the version, step 1 says Ready to Create, keeps Version Settings with its Sync to Apple open, and the build step shows After Step 1 in yellow rather than a missing build. When Apple doesn't have the version yet, the build step says so and offers Sync Version to Apple, which opens step 1 and starts its review. Without a saved plan, Quick Release suggests the version number from every version Apple last reported, and waits a few seconds for the newest material; after that the version starts from the saved material while the download goes on, and when syncing, text this Mac never edited takes App Store Connect's text as it is read at that moment, so the status only reports what was typed here and Add for Review is reached. Text typed here, or kept with Keep Mine, is never replaced, and a field Apple left empty on a new version is filled from the saved listing. Material downloads run ahead of other background reads, also when preparation started them. A version waiting for or in App Review shows Replace the Build on the submitted page: Remove from Review comes first in its own review, and once App Store Connect shows the version as Developer Rejected, Add Build opens so the newer build can be chosen and Add for Review sent again. Each of the three waits for its own approval. Add for Review opens a separate submission approval. Once nothing else is needed, its review is prepared ahead while the step is open, so Add for Review opens the approval at once; nothing is sent before approval. While it waits, it lists each missing item in a shared status row with its command: Sync to Apple for text App Store Connect doesn't have yet, which opens the text review in Add for Review itself so the step stays open, Add Build for a missing build, and Edit for anything else. Only text that first needs a choice or a correction opens What's New in This Version. After any sync the steps are read again from App Store Connect. A status check reads what the open step shows first, such as the version, its text or its build, and the remaining details follow in the background, cheapest first; screenshots at Apple never hold a step back. Once the first step has its status, the other steps are built and read their data behind it, so moving between steps shows each one at once. Each sheet shows the exact change before sending. Sync to Apple opens its sheet on the press: while the review is prepared the sheet shows a progress line and keeps the send command in place as Preparing…, then the changes appear in the same sheet without it closing and opening again. When nothing is prepared, the sheet says why and offers Close. A command pressed inside the open step never scrolls the page; only moving to another step brings its heading into view. After approval the sheet stays open with the sync's progress; Run in Background closes it while the sync goes on, and the window's bottom bar keeps its progress, also on other pages. A sync that stopped shows why on its page. Save Draft keeps work local without opening approval. Submission reuses the version and build already chosen in the flow. Green checks mean ready, yellow means checking, unsaved work, pending sync or approval, and red means missing or invalid required information. A normal prepared update reuses its checked listing and settings; release notes and the new build remain required. Unknown checks never turn green. A version creation blocked by Apple names the current version and state, with a direct link to that platform’s version. Open Version recovery opens the version settings instead of returning to the sync panel. Other listing text and release details start collapsed, with their statuses and Edit commands in shared status rows. Changing steps or closing a section keeps mounted editors and unfinished inputs. Saves, sync reviews and requirement fixes stay on this page. The normal text review sends the quick fields; opening Other Listing Text also enables a text-only review of those additional fields, without sending screenshots. Before Sync to Apple sends text, fields App Store Connect changed while this Mac kept the imported text take Apple's text into the draft, fields outside Quick Release's own that changed on both sides list Use App Store Connect and Keep Mine for a choice first, and text only on this Mac in other fields is sent with the quick fields. When App Store Connect already has the text, the status is read again instead of reporting nothing to publish. A check Apple can't answer keeps its last known result, so a failed read never turns ready steps back into unknown ones, and the version and build stay Not Checked rather than missing until Apple's versions are read. An app already on the App Store shows its countries or regions as Ready to Reuse while the current selection can't be read. While a version is prepared, Apple keeps the live App Information beside the one being prepared; the status compares the editable one, which Sync to Apple writes. Add for Review waits for version text, which carries What's New, until Apple is confirmed to have it, and for reused app information only when Apple is confirmed to differ. In each language editor, Save Draft is available only with unsaved edits, and Sync to Apple rests once App Store Connect has that language's text. What's New in This Version's own Sync to Apple rests the same way once App Store Connect is confirmed to have every language's text.

Overview shows compact release rows whose heading is Continue Release, with Show Status beside it for details. Each account, app, platform and version remembers its expanded or minimized state across visits; changed status and updated plans do not reopen a minimized version. New versions follow the Release Cards default in General settings, initially Expanded. Expand All and Minimize All act on the entire release list. Minimizing the last expanded card can show the native “Minimize all by default?” window-modal popup with Yes, Ask Later and No. The popup overlays its window without adding a card or moving page content. It never appears just from restoring a saved layout. Ask Later postpones it one day; Escape chooses Ask Later. No disables the suggestion until enabled in Settings.

Expanded release details show Apple's current state, up to three requirements and an And More count. The smaller Release card in Apps shows the next requirement and a count for the rest. Missing fields, work to review and unconfirmed checks remain distinct. Submitted versions show their Apple state without repeating old preparation blockers. Reserve summary and feedback tracks so background updates do not move adjacent commands. The app's Release card keeps the workflow grid shared with its other cards. Longer overview release lists use the shared pagination and View Options.

Settings keeps a shared search field above the pane. Search results identify the setting and its pane, and opening a result reveals its section, including settings inside collapsed groups. Searching keeps the current editor mounted, so clearing a query retains unfinished inputs. Moving to a different pane still goes through the existing save and discard review. Search indexes public setting labels and explanations; it never indexes saved account names, credentials or values.

Release states open from their last encrypted local observation and are checked again after unlock. Small version-state reads are shared, limited to two concurrent apps and refreshed periodically behind visible work. Failures retain the last confirmed state and show that its latest check failed. Full preparation follows the configured preparation limit. These reads do not import revisions or send changes to Apple.

In step 3, a language whose text, name, subtitle and screenshots are saved on this Mac but not in App Store Connect yet is one row, marked Ready to Send rather than as a problem; Prepare Review on the same step lists what it uploads. Translate Languages fills every text field of a new language: it translates the description, keywords, promotional text, what's new and subtitle, and copies the app name and every link, such as the privacy policy URL, unchanged. Its results can be taken out again on this Mac: Remove Language for a language that is not in App Store Connect yet, Remove Screenshots for the translated screenshots placed in it, and Remove Added Languages for every language the run added, after one confirmation. The cards stay in Asset Library.

Replacing a build is one place, Release step 4, Build. While the version is Waiting for Review or In Review, the step starts with the Replace the Build card, whose own Remove from Review command opens that change's review. Once App Store Connect shows Developer Rejected, the step reads App Store Connect again at once and then every minute, with a fixed status line under Build to Submit that says it is looking for a newer build, that Apple has received an upload and is processing it, that an upload failed with Apple's first message, or which newer build arrived and when. Uploads come from App Store Connect's build uploads, so one shows before its build is listed; the same line appears while a first version has no build yet. A build still processing can be chosen to see it, but Add Build waits until Apple finishes. A newer processed build is chosen for you unless you chose another one. Every build in the list shows its upload day and 24-hour time. The new build is added on the same step, and Add for Review follows right below it when nothing else is missing. Each part shows its own review and is sent only after you approve it. Step 6 offers Replace the Build, which opens step 4.

Add for Review shows one ordered list of confirmed missing requirements across the release. Resolve Next Item opens the relevant field or step and keeps a return to the submission checklist. Unknown checks remain distinct from missing answers. App Privacy and Tax Category can be completed inside the submission step using their existing forms, local drafts and guarded Apple reviews.

Current Apple state takes precedence over an older failed submission attempt. Waiting for Review and later states show that the version is already submitted; the flow offers its next release step instead of another submission. Preparation commands show why they are unavailable beside the command. A press during a read is retained until the choices settle. Preparing or resuming a review never approves it.

## Dialogs

Every dialog is one of six kinds, chosen by what it shows. The kind sets the size, so dialogs of one kind look the same everywhere, and each dialog uses the smallest kind that fits what it shows. Each keeps its size whatever its content does: the body scrolls, and the commands stay in the footer. The window stays visible around a dialog. A small window keeps a narrow rim, so the dialog has room to work, and the rim grows with the window, so even the largest kind leaves a window of the default size visible above and below it.

Status shows progress or a short result with up to three commands, such as a review being prepared. It is 680 points wide and 260 high.

Confirmation asks a question with up to three answers, such as Save, Discard or Cancel. It is 680 points wide and 280 high.

Question gives a short explanation or choice with its commands, such as error details or turning a feature on. It is 480 points wide and 440 high.

Form holds fields to fill in, such as a key to reconnect or a pricing model to choose. It is 480 points wide and 640 high.

Content shows lists, comparisons, pickers and work in several parts, such as a review of changes, a text comparison or Asset Library. It is 1,040 points wide and 760 high.

Media shows or edits an image or a video at size. It is 1,040 points wide and 780 high.

A dialog whose content changes kind changes size once, when the new content arrives. Sync to Apple opens as a Status dialog while the review is prepared. Its bar shows activity, because how long each step takes is not known, and its text names the step: reading Apple's current version, then comparing it with the saved changes. It becomes a Content dialog when the review with its changes is ready. While it is prepared, Cancel stops the preparation and Run in Background closes the dialog and keeps preparing; the bar at the bottom of the window then follows it. Nothing is sent before the review is approved in either case.

A change that lists many items, one per line, such as a price schedule's countries, shows as one table in the review: a row per item with its value now and after, search, a filter for changed rows and pages. The table scrolls with the dialog's body and never in a scroll area of its own, so the dialog and its commands keep working with a mouse wheel or a trackpad. Short changes keep their before and after text side by side.

## Progress

A bar with an amount is used whenever the amount is known, such as the steps of a sync being sent. Work whose amount is unknown shows the activity bar, a short stretch that moves along the same track, wherever a bar with an amount can follow in the same place; a spinner is for small places, such as beside a command or a status line. A spinner never turns into a bar, and a bar never stands still while work continues. With Reduce Motion the activity bar fades in place instead of moving. Text beside progress names what is happening, never just that something is loading, and work that can be stopped safely has Cancel.

Commands in a dialog follow one order: Cancel on the leading side and the command the person most likely wants on the trailing side, named for what it does, such as Run in Background or Save, never OK.

While saved data opens, Storebench shows a short start screen: the Storebench graphic, the bench mark above the wordmark, and below it a spinner with one line naming the step, such as Opening Storebench or Unlocking saved data, centred on the window's sunken surface. In Dark Mode the app icon and a white name stand in for the dark graphic. The line keeps one fixed track, so the graphic never moves, and the start screen ends as soon as the workspace is ready.

Quitting while started work is still being finished shows what it waits for, such as a sync being sent to App Store Connect, and keeps Quit Now in place. Quit Now stops that work where it is: the sync shows as stopped the next time, and it is never sent again by itself.

## Refresh and sync feedback

Refresh Status updates the current release step's cards and its checklist through one freshness boundary. Matching Apple reads are shared across those cards. Keep editors and their layout mounted while refreshing. With unsaved inputs, show Save, Discard and Cancel: Save uses the existing local draft validators; Discard restores saved drafts; Cancel keeps editing. A changed editor or newer input invalidates an earlier choice. Failed saves keep inputs and stop the refresh.

Library pages and status cards that follow saved state check it again while they are open, but read it again only when something was saved, while a sync, import or check they show is still running, or after half a minute. Refresh always reads.

Current sync cards compare with Apple again after saved fixes and explicit refreshes. A stopped run remains in history; its old refusal is not a current comparison. Show a green check and a checked or synced time beside the material when Apple matches, including when there is nothing left to send. Clear that indication when the inputs change. Preparing a comparison or refreshing a card never approves an Apple write.

Text changed in App Store Connect after a draft took its text is never shown as a change on this Mac. Each field is compared three ways: the last import, the draft's own value and Apple's current text. A field changed at App Store Connect says "Changed in App Store Connect since your draft", and one changed on both sides says so too; each offers Use App Store Connect, which updates the local draft so nothing is sent, and Keep Mine, which leaves the step's review to send this Mac's text with its before and after values. View Changes opens your draft and App Store Connect's text side by side, as a text comparison shows two files. Each panel shows its whole text with its length against Apple's limit and marks the words only it has, red in your draft and green at App Store Connect. When both sides changed, the text the draft took from the last import is one click away. Keep Mine and Use App Store Connect sit under the panels. Keep Mine applies to that exact Apple text, so a later Apple change asks again. Text taken with Use App Store Connect is Apple's, not an edit, so a review never sends it back; typing in the field afterwards makes it this Mac's again. A review is prepared only when every language's saved text is what its editor shows; otherwise that language asks to compare the latest save first and nothing is prepared. Add for Review waits until every such field is settled.

Draft History keeps the earlier text of every saved draft field, newest first, with Copy Earlier Text. Only changed fields are recorded, and each text is stored once however often it is saved.

## Text comparisons

`StorebenchTextDifference` uses the shared word markings: added text is green and bold, removed text is red and struck through. Listing editors expose View Changes beside the changed-field count and in their command footer. The comparison opens a read-only snapshot, shows changed fields together and can compare the import or the loaded draft. Exact before and after text remains available within each field.

## Buttons

Standard buttons share one width, the `action-width` token (192 pt). The width is the same for a button on its own, in a group and as a row command, whatever its label. Buttons of the same size show that they belong together, and buttons of mixed sizes next to each other look inconsistent.

Tell buttons apart by style, not size. `StorebenchButtonStyle` has the variants: primary for the most likely action in a view (one, at most two, per view), secondary for other actions, quiet for low-emphasis commands and danger for destructive ones. A destructive button is never primary.

Primary, secondary and destructive standard actions use macOS push buttons, including system press, focus and disabled states. Quiet commands have no persistent border; their hover and press surfaces provide feedback without competing with the primary action.

Hover looks the same everywhere. Every control follows the pointer through one shared hover core, and every target on a card or dialog shows the same accent border under the pointer: disclosure headings, navigation rows and tiles, tabs and quiet commands also get the light accent fill, with the shared corner radius. Sidebar rows use the page's hover fill, and a selected row looks different from a hovered one. Menus and fields show hover with the accent border, and so do secondary and destructive push buttons; a primary push button turns a darker accent. A record card's heading is its main command across the card's width, such as Continue Release on the Overview's release cards: the whole heading is the target, with the command's name and an arrow at its end, and it shows the shared hover fill and border. Showing the card's details, such as Show Status, is the smaller command beside it, at the standard command width and as tall as the heading. Opening the details reads that release's status from App Store Connect at once. The Overview reads the statuses of the cards on screen first, and how many apps one check reads follows the Performance setting, so a very large account is never read all at once.

Only a few controls size themselves differently. Icon buttons (`size: .icon`) are square at the control height, choice chips such as the date presets use natural widths, and stretched tiles (`stretch: true`) fill their tile up to `action-max-width`. `StorebenchSectionLinks` uses natural-width quiet targets to navigate within a page and wraps them when needed.

Every button keeps the shared control height, `control-height`, and its label on one line.

## Button labels

Write labels in title-style capitalization and start with a verb, such as "Connect Reports", "Sync New Data" or "Add for Review". Short words such as "and", "for", "in", "of", "to" and "with" stay lowercase inside a label. This applies to labels that come from data files too, such as recovery actions and sync modes.

End a label with an ellipsis when the button opens another window, sheet or file panel for more input, such as "Import CSV…" or "Custom…".

A label must fit the shared width, which leaves about 160 pt for 13 pt text. When it does not fit, shorten the label and put the full meaning in `.help(...)`, for example "Open App Review" with the help "Open App Review Information". Never widen the button or let the label wrap.

Use App Store Connect's exact names for its sections, states and actions, shortened only as described above.

The command that sends an approved review uses App Store Connect's own button for that change: Save, Create, Upload, Publish, Confirm, Release This Version, Remove from Review, or TestFlight's Submit for Review, Notify Testers, Invite, Add, Remove and Delete. Add for Review asks once, and its confirmation is Submit to App Review, the same two presses as in App Store Connect. Commands that only open a review, such as Sync to Apple or Prepare Review, never send anything; the review's own command does.

## Button groups and footers

`StorebenchActionGroup` places related buttons in a row at the shared width and wraps them into complete rows on narrow windows. Groups start on the same leading edge as the text they belong to.

`StorebenchFormFooter` is the final command area of a card or form, below a divider. Put the primary action first. Contextual editor footers span the form width even when nested inside a command group; only individual buttons use button-sized cells. Group Save Draft and Sync to Apple inside the same contextual footer, and keep Refresh beside the card heading. Every change that reaches App Store Connect uses the same two commands: Save Draft keeps it on this Mac, and Sync to Apple saves it first and opens a review that names the exact change, such as creating version 3.0 or adding build 76, before anything is sent. A step has one Sync to Apple; a review shown below it has no second one. A contextual footer sits under a divider rather than in its own box, so its commands end on the card's trailing command column. Options a disclosure shows start under its label, while a card inside it keeps the page's grid and lines up with the cards beside it. Every multi-line field is the same resizable text box with its resize handle and Reset below it. With the pointer over it, a long text box scrolls its own text and shows a scroll bar, without clicking into it, and hands the scroll to the page once its text ends in that direction; a box being edited always scrolls itself. While App Store Connect keeps the live App Information beside one being prepared, each language's app name, subtitle and privacy fields show once and a change goes to every record of the language, as they are saved and synced together; the release check uses their shared values, or the one being prepared when they differ. Feedback and explanations share the full copy track instead of wrapping inside a narrow button column.

`StorebenchCommand` is a button that can be busy or unavailable; its reason shows as hover help, so the button stays in place instead of disappearing.

## Where controls belong

Every button, spinner and progress bar sits in a shared component that owns its place, never loose in a card body or beside text in an ad-hoc row.

- Read and refresh commands go in the card header through the card's accessory or actions.
- The card's work goes in `StorebenchFormFooter` or the editor footer.
- Related commands inside a step, disclosure or record go in `StorebenchActionGroup`, and natural-width choice chips such as date presets go in `StorebenchChipGroup`.
- A record line with its own commands uses `StorebenchActionRow`: the copy on the leading track and the commands on a trailing track that moves under the copy in narrow windows.
- A command that acts on one field uses `StorebenchInputActions`, `StorebenchFieldCommands` or the field's accessory.
- A table's command column uses `StorebenchTableActions`, and a record name that opens its record uses `StorebenchRecordLink`.
- A preview that opens, enlarges or plays itself uses `StorebenchMediaButton`; while its file is read, `StorebenchMediaStatus` shows the spinner or the reason nothing is drawn.
- A running operation shows one `StorebenchProgressStatus` line, with a bar when its amount is known and its label in a fixed track. Loading content uses `StorebenchLoadingStatus`. A step that is running or failed shows `StorebenchStepState` beside its name.
- Ranked shares, such as the leading territories, use `StorebenchShareRow`; its bar is a measure, not progress.

Inputs share one look. Text fields, selections and choices of several values have the same height, background, border, hover border and focus ring; a selection keeps macOS's menu, keyboard and VoiceOver behavior inside that field rather than drawing the system pop-up bezel. A required choice is never folded away. Disclosures hold secondary details, as Apple's guidelines describe. A choice of several values, such as the languages Translate Languages fills, is a field beside the related picker that names what is chosen and opens a dialog with quick choices and every option. Translate Languages starts with the version's own other languages, or the largest App Store markets when the version has only one, so it can run at once.

## Status rows

`StorebenchStatusRow` is the list row for sources, checks and history items. It has fixed columns, so rows line up from row to row and screen to screen:

- the title and detail on the leading side, growing to fit their text
- the status, such as a sync badge or a state, in one column of `statusColumn` width (124 pt)
- the row command, such as Open, Change or Open Review, in the trailing column at the shared button width
- extra buttons for the row, such as recovery actions, in a group under the title at the shared width

Do not pass a custom command width. On narrow windows the row stacks: the title above, then the status and the command on one line.

`StorebenchSyncBadge` fills the status column, so every badge has the same width whatever its label.

A closed record can show `StorebenchGlance` beside its title: App Store Connect's tone mark with a short headline and one detail line, in a fixed 300 pt track, so a record says how it stands without being expanded. On Overview, each app in Data status shows how many sources are synced, what needs attention or is still waiting, and the last sync's day and 24-hour time; a running sync shows a spinner and how many sources are checked.

## Text and status areas

Reserve space for labels, hints, status and comparisons before they appear, so updates never move the layout. Static text grows to show all of it, up to about eight lines, then scrolls. Live status and feedback, such as `StorebenchFeedback` and `StorebenchTextSlot`, keep a fixed height sized for realistic messages. Nothing is clipped without a way to read it.

An Edit action reveals its section and requests keyboard focus through the shared text control. Keep the native input mounted when saving or ending a focused edit. Field feedback and Done actions reserve their tracks before they appear. Expanding sections and revealing fields use an immediate layout update, so scrolling does not compete with animated changes in editor height.

Media edits opened from the release checklist use `StorebenchEditorGuide`: a named section, complete instructions and a Done action within one padded surface. Explain that Done saves locally and returns to the checklist, while Sync to Apple opens a separate review. Static instructions grow with their text; narrow panes place the command below them. Keep the guide separate from the media cards that follow, with the shared section gap between their borders.

Field focus frames extend 8 pt into the surrounding padding. They never touch the input or its feedback, and showing or hiding a frame never changes the editor's geometry. Do not draw a focus surface behind nested media cards or place unpadded instructions on its edge.

Cards that share a row share its height, so their buttons sit on one bottom edge.

## Icons and colors

Icons come from the registry in `design.json` through `StorebenchIcon`; do not use system symbols directly. Native menus use template images drawn from the same registry. Colors come from the named tokens through `StorebenchTheme.color(_:)`, with light, dark and increased-contrast values for each. Native table surfaces, alternating rows and search fields use macOS semantic colors and control rendering.
